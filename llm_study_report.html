Two distinct failure modes:

  • Tight-loop waste (27.8% of g55's truly-wasted ≈ 23 700 reads):

read (0, 200), do 2–10 intervening turns, then read (0, 220) — same content, different cap. With 8 K compaction the model gets ~identical head/tail back from both. The api_response between the two reads emits only ~50 output tokens — barely any visible reasoning. Closest thing to "irrational" in the data.

  • Far-back refresh (~70% of g55's truly-wasted ≈ 60 000 reads):

re-read a file hundreds of turns later. Verified example: phase3_worker_implement.md read at event #73 and #258 (185 events apart), no intervening modification. Defensible as a recency-salience workaround in long agent loops, but expensive.

Why does g55 do this and cond doesn't? Best evidence-grounded answer: not a schema bug (both see identical tool schema), not a cap difference (both at 8 K), not a missing parameter (g55 uses non-zero offsets in 39.7% of calls). The compounding factor is per-turn output density. Median output_tokens/turn:

role g55 cond
worker_implement 70 229
strategist 336 1 166

g55 emits ~3× less per turn → less in-context self-summary of what it already read → more refresh-via-re-read needed for older content. The tight-loop "vary the limit" pattern is a separate quirk: the model between two reads emits ~50 output tokens, hardly any visible reasoning, then tries a slightly different cap. Each per-decision step is defensible (verify a write, see the trimmed middle, refresh fading context), but they compound into 28× the truly-wasted volume.

The takeaway is not "GPT-5.5 is broken". It's that the same prompt and same cap produces materially different behavior depending on how densely the model talks per turn. Raising tool_output_max_chars (which you've now done) eliminates the compaction-driven re-reads. The remaining tight-loop and far-back-refresh patterns are model-shaped and would need a prompt rule ("you have prior file content; do not re-read unless modified or you need a range outside your prior reads") to fully address.

H4 (g55 paginates everything, cond reads whole files) — CONFIRMED, and the pattern is even more specific.

Param shape distribution:

shape g55 cond
no offset, no limit (defaults — whole file) 0 (0.0%) 3 640 (35.8%)
limit only 0 (0.0%) 728 (7.2%)
offset only 0 (0.0%) 29 (0.3%)

g55 specifies both parameters on every single read_file call. Not one default-args call across 133 562 reads. Same tool schema for both LLMs — this is a learned behavior, not an API limitation.

Tool schema is bit-identical for both LLMs. I pulled the actual api_request.tools[] payload from one g55 and one cond worker log; the read_file schema (including the description "Use offset and limit to read portions of large files" and the offset parameter with "default 0") is byte-for-byte the same. So the discrepancy is not a prompt or schema bug — both LLMs are told about both parameters.

tool_output_max_chars was identical at runtime — 8 000 chars (the default) on both runs. Verified from the logs, not the config file (the configs were overwritten after the runs). Method: for every api_request, walk the conversation history and find compacted outputs containing [...trimmed N chars...]; their total length ≈ max_chars. Result on real data: 900 compacted outputs sampled on g55 and 24 on cond all cluster in the 8027–8030-char band. So the cap was 8 000 for both, applied uniformly across every agent (conductor, strategist, workers, supervisor, reporter, phase 0/1/2 — all 13 AgentLoop(...) callsites pass the same self.config).

The cap is identical and so cannot differentially explain g55's re-read behavior. But it makes one specific failure mode much worse on g55: at 8 KB compaction, most code files get head/tail trimmed (first ~4 000 chars + marker + last ~4 000 chars). When g55 asks for (0, 200) then (0, 220) then (0, 120) on the same file, each compacted result is nearly identical — same first 4 000 chars, same last 4 000 chars, only a different trim count in between. g55's "vary the limit, anchor at offset 0" pattern is therefore extra wasteful: it re-receives essentially the same 8 KB view each time. cond's pattern of moving the offset ((500, 500), (1000, 500)) pulls different head+tail regions because the compacted window covers a different slice of the file.

g55 does use non-zero offsets — 52 980 calls (39.7%) have offset > 0, spread across 2 152 distinct values. So the agent demonstrably knows the parameter exists. The most-common single combinations all use offset = 0 because that bucket has many fewer distinct values to spread across; the non-zero-offset half spreads across thousands of values.

Synthesized explanation

The 13× read_file ratio is not a single failure. It's three reinforcing factors:

  1. g55 emits 3× less per turn (median 70 output tokens vs 229). Smaller outputs → smaller accumulated history → ~half the per-turn context (54 k vs 98 k input_tokens) → must refetch state via read_file.
  2. g55 never reads full files (0 full reads vs cond's 3 640). Always paginates with offset/limit → multiple calls to retrieve the same logical content.
  3. g55 thrashes (mean 11.2 implement assignments per experiment vs cond's 1.3). Each fresh worker turn starts cold and re-reads the framework + experiment files from scratch.

What it is not:

  • It is not "g55 is fed less context" — g55 is fed less, but that's a

consequence of (1), not an upstream input choice.

  • It is not "g55 gets truncated read results" — call-for-call file

bandwidth is the same on both.

  • It is not "g55 paginates the same file in tight succession to read

faster" — cond does that more (median 10 s re-read interval, 70.5% within 30 s); g55's re-reads are mostly across-turn (median 123 s, 44.1% within 30 s).

Productive? Three signals that say no:

  • On clean experiments, g55 still makes 35% more reads to accomplish the

same work the kanban accepts from cond.

  • Despite 13× more file reads, g55 still has 30.5% blocked transitions

and 24% smoke refusals; cond with 1/13 the reads has 0.7% and 0%. The reads do not translate into better state.

  • The most-read paths (top of the list below) overlap exactly with the

most-thrashed experiments — re-reading is the symptom, not the remedy.

What each LLM is good at / bad at

GPT-5.5 (g55) — strengths

  • Faster per-API-roundtrip latency (median 5.0s vs 10.4s) — when the

conversation is short it gets through it quickly.

  • Larger code output per experiment (~2× LOC) — more aggressive

scaffolding, more ablation branches in strategy code.

  • More extensive use of persistent memory (search + read 2× more often).
  • Higher-Sharpe "frontier" results on the proxy metric (largely an

artifact, see caveat above).

GPT-5.5 (g55) — weaknesses

  • Kanban indiscipline. 30.5% of status-attempts blocked, 24% of

results refused as smoke, 44% of update_experiment calls are idempotent no-ops. Reaches for terminal states (finished/running) from implemented, skipping the → checked step.

  • Reassignment loops. Mean 11.18 implement assignments per

experiment, max 420 on a single row. The implement worker repeatedly re-reads existing code, re-runs smoke, and exits without changing state.

  • Out-of-band canonical launches. 28 experiments where nohup … run_experiment.py

was launched directly, bypassing the dispatcher. Each one becomes a kanban zombie.

  • Smoke laundering. 773 attempts to ship a smoke-flagged payload as

canonical results — caught by the guard, but it tells you the LLM's default is "any metrics are leaderboard metrics".

  • Conductor needs to clean up. g55's Conductor issued 2 phase rewinds

and 27 throttles to keep the pipeline upright; cond's needed neither.

  • Bloated debriefs. 275 "Verification refresh" sections across all

debriefs, vs 10 on cond. Some debriefs are 4 200 lines of mostly duplicated content.

  • Higher error rate. 141 DB rows with errors (cond 49); 24 of them

are local_cpu canonical attempt TIMEOUT.

Claude Opus 4.7 (cond) — strengths

  • Clean kanban. 93% of update_experiment calls actually advance state.

Almost never invents a status transition.

  • Linear progression. ~1 implement assignment per experiment (mean

1.31, max 14) — the implement worker does its job and hands off.

  • No smoke laundering at all. 0 refused payloads.
  • Cheaper per useful unit. 4× fewer tool calls, 4× fewer requests,

1.7× less LLM time per analyzed experiment.

  • Lower-volume Conductor. Fewer overall interventions but they're

targeted (parking, priority, annotation) rather than firefighting (throttle, rewind, retrospective).

  • Heavier shell use — composes longer bash pipelines (50% of all

tool calls are shell_exec) and re-reads files less; behavior aligns with the prompt's "explore the framework, then go" rhythm.

  • Proactive in Phase 1. Built the entire backtest/ framework

during exploration (88 framework-creating tool calls in conversation.jsonl), skipping the dedicated Phase 2 builder step entirely. Phase 2 critic passed on iteration #1. g55 left framework construction to Phase 2 and needed 6 builder→critic iterations to reach PASS.

Claude Opus 4.7 (cond) — weaknesses

  • Slower per request. Median 10.4s vs g55's 5.0s; cond's max single

request is shorter (953s vs 2714s) but typical responses take twice as long.

  • Less mechanism diversity in some families. Heavy on

catboost / GRU / EWMA-stacker recipes; lighter on graph-based and novel-architecture experiments.

  • Sharpe values cluster lower — could be a true conservatism or

could be missing the "find high-Sharpe (maybe leaky)" risk taking that exposes label issues. Without an external audit this is ambiguous.

  • Larger pending backlog. 94 experiments at to_implement waiting,

because the implement workers are slower per-experiment even when they go through cleanly.

  • Strategist still verbose. strategist LLM time 33h, similar to g55

proportionally.

  • Crosses role boundaries. Doing Phase 2's framework-build during

Phase 1 exploration is helpful here but is a discipline-violation in spirit — Phase 1's prompt says explore, not build. If you depend on the kanban boundary for sandboxing/review, this is something to watch.

Recommendations

These are derived from the data above, not anecdote.

1. Default to Claude Opus 4.7 for autonomous-research pipelines

On every measured efficiency axis cond wins by 2–10×. Same configuration, same prompts, same dataset. The throughput-per-LLM-hour advantage compounds across the entire run.

2. Tighten the implement-worker prompt against the GPT-5.5 failure modes

Even if you keep using GPT-5.5 for some roles, the prompt should explicitly forbid the patterns the data shows it falling into:

  • No out-of-band python run_experiment.py / nohup launches
  • Always go implemented → checked; never reach for finished / running /

done / analyzed directly

  • Never store smoke-flagged metrics; never invent ad-hoc run_scope strings
  • When the canonical run is blocked by a missing precondition, set

error="blocked: <reason>" (the new dispatcher honors this prefix to stop re-assigning); never write a results_json with canonical_full_run: false

(All four rules now live in src/alpha_lab/prompts.py::_IMPLEMENT_LIFECYCLE_GUARDRAIL and are appended generically by build_step_prompt.)

3. Land the dispatcher auto-promote (already done)

set_results now auto-promotes implemented / checked → finished when a canonical payload lands, regardless of which LLM is driving. This breaks the worst observed pattern on g55 (25 zombie rows) at the infrastructure level so the next run will not strand them no matter how the LLM behaves.

4. Run shorter pretests on new LLMs before committing budget

A 30-minute smoke pipeline using each candidate LLM would surface the g55-style 30.5%-blocked / 24.2%-refused signatures within a few hundred update_experiment calls — long before you commit a 100-hour budget. Status-update outcome ratios are an excellent early proxy for whether an LLM understands the kanban contract.

5. Make the strategist explicitly trade off mechanism diversity vs depth

g55 hit far more "novel" mechanisms (graph-based, stake-based, ranking variants) but burned its budget retrying broken implementations of them. cond stayed close to a proven core (catboost / GRU / EWMA ensemble) and finished what it started. A per-strategist parameter for breadth-vs-depth (currently implicit in the prompt) would let operators choose.

6. Cap LLM thrashing on a single experiment

Even with the auto-promote and the prompt fixes, a hard max_implement_assignments_per_experiment cap in the dispatcher (e.g. 5) would have saved hundreds of hours on g55. After the cap, auto-cancelled with a clear message. cond would essentially never hit this cap (it stays at 1–2). g55 would.

7. Use Conductor interventions as a health signal

g55's Conductor issued 27 throttles + 2 phase rewinds + 149 retrospectives. If those counts cross a threshold the operator should be alerted that the pipeline is in firefighting mode and consider intervening. cond's Conductor needed almost none of these — a healthy run looks like steady parking + priority adjustment.

8. Audit "high Sharpe" outliers on g55-style runs

The 14.29 / 12.38 / 10.63 Sharpes on g55's top experiments are flagged by the milestone reports themselves as proxy-not-PnL. Build an automatic post-hoc audit that re-evaluates the top-N by a stricter (return-bridge) metric before the reporter promotes them — the cap_aware_realized_return_bridge_audit experiment in g55 already shows this pattern (proxy 4.65 → realized 0.105). Without that audit, "frontier" Sharpe values on the leaderboard mislead.

9. Cache and time pytest invocations on NFS-mounted venvs

Not LLM-specific, but observed during this study: the pytest suite is ~7 s of actual test time but takes ~25 s+ per cold invocation. For a dev loop, PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 pytest tests/<file>.py cuts that to roughly the bare-Python import cost.

10. Build per-LLM dashboards as a first-class deliverable of every run

The numbers above are extractable in a few minutes from a structured cache of the logs. Wiring a small standing dashboard (kanban-block %, smoke-refusal %, implement-vs-analyze ratio, LLM-time-per-analyzed) into the dispatcher's milestone output would let operators see at a glance whether they are in "cond-shaped" or "g55-shaped" territory and act early.
